## 1. Why this experiment

The repository's central hypothesis is that a small frozen LLM plus a
rewritable memory sidecar can approximate some capabilities of a larger LLM.
The existing bAbI/reproduction work already shows that a position-aligned
writer/reader can transfer source information into an application prompt. What
was not tested is a *multi-commit, versioned-fact* setting: several separate
source documents, each a commit, and questions whose answers live in different
commits. A last-commit-only baseline is therefore essential. The experiment is
designed to separate:

1. **storage** — can the writer put the facts into memory;
2. **retrieval** — can the reader address the right fact for a question;
3. **temporal/versioned use** — can the model distinguish current, previous,
   and original locations;
4. **task adaptation** — whether gains come from memory or from LoRA/parametric
   fitting.

Claim under test: *a frozen Qwen3-1.7B with a position-aligned writable memory
sidecar can answer questions supported by earlier commits, not only the last
commit, on a synthetic versioned-location task.* Falsification: memory accuracy
is no better than `last_commit_only`, `null_memory`, or `shuffled_memory`, and
counterfactual source edits do not change predictions.

## 2. Experiment A — complex multi-person versioned facts (negative)

Dataset: 3 commits, 3 people, two movers, 12 cities, train/test names disjoint,
1200 train episodes / 300 test episodes, 5 questions per episode (3600 current,
2400 previous). Generated with seed `20261125`; files under
`datasets/multicommit-memory/`; SHA-256:
`train e0dc3fce...b86b95f`, `test eb0049cb...fcece7`.

Training: Qwen3-1.7B frozen, position-aligned memory width 1024, writer/reader
heads 8, injection after `[0,1,2,3]`, gate bias `-6`, source and application
LoRA rank 8, batch 8.

| Run | Result |
|---|---|
| 1000 steps, lr 3e-4 | memory 9.0%, full_context 60.3%, last_commit_only 9.0%, no_source 7.5%, null_memory 7.7%, shuffled_memory 9.0% |
| 3000 steps, lr 3e-4 | loss became `NaN` at step 1600 and stayed `NaN`; checkpoint not usable |
| 1200 steps, lr 1e-4, source LoRA, gate `-2`, clip 1.0 | memory 11.0%, full_context 62.0%, last_commit_only 8.0%, no_source 8.7%, null_memory 8.3%, shuffled_memory 11.0%, counterfactual follow 12.7% / resist 8.7% |

Interpretation: this task did **not** show causal multi-commit memory. Memory,
last-commit-only, and shuffled memory all sat near chance (~8–11%), so the
application-side adaptation appears to learn a weak prior rather than a
source-specific retrieval rule. The `NaN` run also shows optimization fragility
at the original learning rate. This is a boundary result, not evidence that the
architecture cannot store facts.

## 3. Experiment B — single-entity three-commit diagnostic (positive)

Dataset: one entity, three commits, 6 cities, 6 train names / 6 unseen test
names; questions probe `current`, `previous`, and `original` location. Each
source document is a separate commit. Generated by
`experiments/multicommit-memory/generate_simple.py`, seed `20261125`;
2000 train episodes / 400 test episodes (6000 / 1200 examples). Hashes:
`train e8cd120c3714a094bba785da69907ed251bcbc15be6b4dec2119489d7b6e3de8`,
`test 34e765d656f4e72497326d8a28210f81677c0466bdc10c6ca199f55bf051d9e7`.

Checkpoint: `runs/multicommit-memory/simple3.pt`, step 1500. Config: memory
width 1024, 8 heads, injection `[0,1,2,3]`, gate bias `-2`, source + application
LoRA rank 8, lr `1e-4`, batch 8, gradient clip 1.0. Train loss fell from 3.45 to
~7e-4.

Test results (1200 examples, unseen names):

| Variant | Accuracy | Current | Previous | Original |
|---|---:|---:|---:|---:|
| `memory` (all 3 commits) | **99.75%** | 99.75% | 100.0% | 99.5% |
| `full_context` | 86.08% | 100.0% | 58.25% | 100.0% |
| `last_commit_only` | 50.25% | 100.0% | 47.5% | **3.25%** |
| `shuffled_memory` (memory from another episode) | 72.33% | 99.75% | 17.75% | 99.5% |
| `null_memory` (zeroed cells) | 16.83% | 14.5% | 20.0% | 16.0% |
| `no_source` (application only) | 17.33% | 14.5% | 20.0% | 17.5% |
| counterfactual memory | follow 99.83% / resist 0.0% | — | — | — |

Interpretation: this is a positive, causal multi-commit result for the simple
single-entity case. `last_commit_only` answers current facts but almost never
answers the original fact (3.25%); full context also struggles on `previous`
(58.25%). The trained memory answers all three question types near ceiling, and
counterfactual source edits are followed. The `shuffled_memory` control is high
on current/original because another episode's memory can contain the same city
by chance, but it collapses on `previous` (17.75%), so temporal order matters.
This supports a narrow claim about one entity and ordered commits; it does not
show multi-person binding.

## 4. Experiment C — two-entity boundary probe (negative / boundary)

Dataset: one mover (three commits) and one stayer (two commits), 6 cities, 5
questions per episode (current/previous/original for mover; current/previous for
stayer), 2000 train episodes / 400 test episodes. Generated by
`experiments/multicommit-memory/generate_two.py`, seed `20261125`; hashes
`train 9b51e44b...b5d6b1`, `test 1e2634a3...4cde8`. Checkpoint:
`runs/multicommit-memory/two.pt`, step 1500, same config as B.

Evaluation: the 1500-step checkpoint was evaluated on the first 400 test
examples only; the 3000-step checkpoint was evaluated on all 2000 test examples.

| Checkpoint | Variant | Accuracy | current | previous | original |
|---|---:|---:|---:|---:|---:|
| `two.pt` (1500 steps, 400 examples) | `memory` | 15.25% | 15.6% | 13.1% | 18.75% |
| `two.pt` (1500 steps, 400 examples) | `full_context` | **80.0%** | 89.4% | 60.6% | 100.0% |
| `two.pt` (1500 steps, 400 examples) | `last_commit_only` | 15.0% | 14.4% | 14.4% | 17.5% |
| `two.pt` (1500 steps, 400 examples) | `shuffled_memory` | 15.5% | 15.6% | 13.75% | 18.75% |
| `two_long.pt` (3000 steps, 2000 examples) | `memory` | **53.75%** | 38.125% | 46.375% | 99.75% |
| `two_long.pt` (3000 steps, 2000 examples) | `full_context` | **81.45%** | 89.75% | 63.875% | 100.0% |
| `two_long.pt` (3000 steps, 2000 examples) | `last_commit_only` | 26.25% | 21.875% | 36.875% | 13.75% |
| `two_long.pt` (3000 steps, 2000 examples) | `shuffled_memory` | 47.35% | 38.125% | 30.375% | 99.75% |
| `two_long.pt` (3000 steps, 2000 examples) | `null_memory` | 16.0% | 17.375% | 16.0% | 13.25% |
| `two_long.pt` (3000 steps, 2000 examples) | `no_source` | 15.65% | 17.375% | 16.0% | 11.5% |
| `two_long.pt` (3000 steps, 2000 examples) | counterfactual | follow 55.5% / resist 9.85% | — | — | — |

Interpretation: the 1500-step checkpoint is undertrained and near chance, so it
is not a clean architecture verdict. At 3000 steps the memory learns the
`original` question almost perfectly (99.75%) and reaches 53.75% overall, but
`current` (38.125%) and `previous` (46.375%) remain well below full context
(81.45%). Last-commit-only is 26.25% and shuffled memory 47.35%, so the gain is
only partly source-specific. This is a **partial / boundary** result: the
position-aligned reader does not bind two independent entity histories at the
single-entity level. The single-entity claim should not be generalized to
multi-entity memory without a new mechanism (explicit entity slots or
entity-specific query keys).

## 5. What is established

- A position-aligned memory sidecar can, in the simple ordered single-entity
  setting, answer facts from earlier commits, not only the last commit.
- The gain is source/memory-specific: `null_memory` and `no_source` stay near
  chance, and counterfactual source edits are followed.
- `last_commit_only` fails specifically on the original fact, which is the
  cleanest multi-commit discriminator.
- A complex multi-person synthetic task did not learn causal multi-commit
  retrieval at 1000–1200 steps; the 1500-step two-entity checkpoint is
  undertrained (15.25%), while the 3000-step checkpoint reaches 53.75% memory
  accuracy versus 81.45% full context. This is a boundary/partial result, not a
  refutation of storage.

## 6. What is not established

- General multi-entity binding, interference, or overwrite semantics.
- Robustness to novel names beyond this generator (the simple test used unseen
  names, but only one generator and one seed).
- Whether the model would answer free-form generation, not candidate likelihood.
- Whether the result scales to larger memories, more commits, or real corpora.
- The exact cause of the complex-task failure: capacity, optimization, gate
  initialization, question ambiguity, or task difficulty.
- Statistical significance beyond the large observed gaps; no multi-seed
  replication yet.

## 8. Next steps

1. Treat the claim as **single-entity, ordered commits** only. The two-entity
   probe is undertrained at 1500 steps and reaches only 53.75% at 3000 steps
   versus 81.45% full context, so do not extend it to multi-entity binding.
2. Run a second seed and a same-name held-out split to test generator/name
   dependence.
3. Diagnose why the writer/reader fails on two entities: the `current` and
   `previous` questions remain much lower than full context even after 3000
   steps; test explicit entity-slot allocation, per-entity query keys, or a
   reader that selects by name rather than by raw position.
4. Do not tune the complex-task architecture further until the boundary is
   clear; preserve the negative/partial runs and controls.
5. Keep all work local; no remote push or issue creation was performed.
