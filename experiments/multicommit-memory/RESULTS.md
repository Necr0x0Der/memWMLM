# RESULTS — multi-commit memory

Date: 2026-11-25
Branch: `multicommit-memory`; pushed to `origin`; PR #17 open against `main`
Backbone: `Qwen/Qwen3-1.7B`, revision `70d244cc86ccca08cf5af4e1e306ecf908b1ad5e`
Environment: Python with torch `2.9.0+cu128` and `transformers 4.57.3`
GPU: RTX 4090

## Claim

A frozen small LLM with a position-aligned writable memory sidecar can answer
questions whose supporting fact is in an earlier commit, not only the last
commit, in a synthetic single-entity versioned-location task. This is a narrow
claim about storage, retrieval, and ordered commits; it is not a general claim
about multi-entity memory.

## Experiment 1 — single-entity, three commits (positive)

Dataset: `datasets/multicommit-simple3/`; generated by
`experiments/multicommit-memory/generate_simple.py`, seed `20261125`.
2000 train episodes, 400 test episodes; 3 questions per episode
(`current`, `original`, `previous`); 6 cities; train/test entity names disjoint.
Train examples 6000, test examples 1200.

SHA-256:
- train: `e8cd120c3714a094bba785da69907ed251bcbc15be6b4dec2119489d7b6e3de8`
- test: `34e765d656f4e72497326d8a28210f81677c0466bdc10c6ca199f55bf051d9e7`

Checkpoint: `runs/multicommit-memory/simple3.pt`, step 1500.
Config: memory width 1024, writer/reader heads 8, injection `[0,1,2,3]`,
gate bias `-2`, source and application LoRA rank 8, lr `1e-4`, batch 8,
gradient clip 1.0. Train loss: 3.453 at step 1; ~0.000713 at step 1500.

Test results (1200 examples):

| Variant | Accuracy | current | previous | original |
|---|---:|---:|---:|---:|
| `memory` (all 3 commits) | **0.9975** | 0.9975 | 1.0000 | 0.9950 |
| `full_context` | 0.8608 | 1.0000 | 0.5825 | 1.0000 |
| `last_commit_only` | 0.5025 | 1.0000 | 0.4750 | **0.0325** |
| `shuffled_memory` (memory from another episode) | 0.7233 | 0.9975 | 0.1775 | 0.9950 |
| `null_memory` | 0.1683 | 0.1450 | 0.2000 | 0.1600 |
| `no_source` | 0.1733 | 0.1450 | 0.2000 | 0.1750 |
| counterfactual memory | follow 0.9983 / resist 0.0000 | — | — | — |

Interpretation: the memory model answers facts from commit 1 and commit 2, not
only commit 3. The `original` question is the clean discriminator:
last-commit-only is 3.25%, full memory 99.5%. The `previous` question is also
better under memory (100%) than full context (58.25%). `null_memory` and
`no_source` remain near chance. Counterfactual source edits are followed, so
the predictions causally depend on the runtime memory.

Caveats:
- One synthetic generator, one seed, one checkpoint. No multi-seed replication.
- Candidate-likelihood scoring over six city names, not free-form generation.
- Test entity names are unseen, but the generator's grammar and city vocabulary
  are fixed.
- `shuffled_memory` is memory from a different episode; because the city
  vocabulary is small, current/original can match by chance. It collapses on
  `previous` (17.75%), which is the temporal-order signal.
- The model still has application-side LoRA; memory gain is not isolated from
  task adaptation.

## Experiment 2 — complex three-person task (negative / boundary)

Dataset: `datasets/multicommit-memory/`; 3 commits, 3 people, two movers,
12 cities, 1200 train / 300 test episodes, 5 questions per episode.
Train SHA-256 `e0dc3fcebc464c75284b002fbee53a21c69ff67b0bb72fc38f55f1df6b86b95f`;
test SHA-256 `eb0049cb3aff9f4cd11c85a98ebd5f54f777eff5bc9055d472a9ad10d6fcece7`.

| Run | memory | full_context | last_commit_only | null_memory | shuffled_memory | no_source |
|---|---:|---:|---:|---:|---:|---:|
| 1000 steps, lr 3e-4 | 0.090 | 0.6033 | 0.090 | 0.0773 | 0.090 | 0.0747 |
| 1200 steps, lr 1e-4, source LoRA, gate -2, clip 1.0 | 0.110 | 0.620 | 0.080 | 0.0833 | 0.110 | 0.0867 |

The 3000-step lr 3e-4 run hit `NaN` at step 1600 and stayed `NaN`; its
checkpoint is not valid for evaluation.

Interpretation: this task did not produce causal multi-commit retrieval. Memory,
last-commit-only, and shuffled memory are all near chance, and the
application-side adaptation appears to learn a weak prior. This is a boundary
result: it does not prove the writer cannot store facts, but it shows that the
simple single-entity success does not automatically extend to multi-person
binding and temporal relations.

Possible confounders: 12-city answer vocabulary, two movers per episode,
question ambiguity, gate initialization, lower effective training time, and
optimization instability. These were not isolated in a factorial ablation.

## Experiment 3 — two-entity boundary probe (negative)

Dataset: `datasets/multicommit-two/`; one mover (three commits) and one stayer
(two commits), 6 cities, 5 questions per episode, 2000 train / 400 test
episodes. SHA-256:
- train: `9b51e44b6bcce499dbf3c92879cd50c5fbe15a6ed27f00f98efb8e94bcb5d6b1`
- test: `1e2634a3e96e839b109cc7b44311cf94901b58da4c8ff66ad441e4471364cde8`

Checkpoint: `runs/multicommit-memory/two.pt`, step 1500, evaluated on the first
400 test examples; longer run `runs/multicommit-memory/two_long.pt`, step 3000,
evaluated on all 2000 test examples. Same settings as Experiment 1.

| Checkpoint | Variant | Accuracy | current | previous | original |
|---|---:|---:|---:|---:|---:|
| `two.pt` 1500 (400 ex.) | `memory` | 0.1525 | 0.15625 | 0.13125 | 0.1875 |
| `two.pt` 1500 (400 ex.) | `full_context` | **0.8000** | 0.89375 | 0.60625 | 1.0000 |
| `two.pt` 1500 (400 ex.) | `last_commit_only` | 0.1500 | 0.14375 | 0.14375 | 0.1750 |
| `two.pt` 1500 (400 ex.) | `shuffled_memory` | 0.1550 | 0.15625 | 0.1375 | 0.1875 |
| `two_long.pt` 3000 (2000 ex.) | `memory` | **0.5375** | 0.38125 | 0.46375 | 0.9975 |
| `two_long.pt` 3000 (2000 ex.) | `full_context` | **0.8145** | 0.8975 | 0.63875 | 1.0000 |
| `two_long.pt` 3000 (2000 ex.) | `last_commit_only` | 0.2625 | 0.21875 | 0.36875 | 0.1375 |
| `two_long.pt` 3000 (2000 ex.) | `shuffled_memory` | 0.4735 | 0.38125 | 0.30375 | 0.9975 |
| `two_long.pt` 3000 (2000 ex.) | `null_memory` | 0.1600 | 0.17375 | 0.1600 | 0.1325 |
| `two_long.pt` 3000 (2000 ex.) | `no_source` | 0.1565 | 0.17375 | 0.1600 | 0.1150 |
| `two_long.pt` 3000 (2000 ex.) | counterfactual | follow 0.5550 / resist 0.0985 | — | — | — |

Interpretation: the 1500-step checkpoint is undertrained and near chance, so it
is not a clean architecture verdict. At 3000 steps the memory learns the
`original` question almost perfectly (99.75%) and reaches 53.75% overall, but
`current` (38.125%) and `previous` (46.375%) remain well below full context
(81.45%). Last-commit-only is 26.25% and shuffled memory 47.35%, so the gain is
only partly source-specific. This is a **partial / boundary** result: the
position-aligned reader does not bind two independent entity histories at the
single-entity level. The single-entity claim should not be generalized to
multi-entity memory without a new mechanism (explicit entity slots or
entity-specific query keys).

## What remains unproven

- General multi-entity binding, interference, and overwrite semantics; the
  two-entity probe reaches only 53.75% memory accuracy at 3000 steps versus
  81.45% full context, and the `current`/`previous` questions remain low.
- Whether the result survives a second seed, a same-name held-out split, or a
  different commit ordering.
- Whether the model can produce free-form answers rather than candidate scores.
- Whether larger memories or more commits improve or degrade retrieval.
- The mechanism behind the two-entity partial failure and complex-task failure;
  no factorial ablation was run.
- Statistical significance beyond the large observed gaps; no confidence
  intervals or multi-run replication.
